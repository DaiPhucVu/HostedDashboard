# Ranking V2 and Automatic Assignment Plan

## Objective

Replace placeholder-like provider scores with deterministic features derived from
Firebase provider profiles, job history, and customer reviews. Qwen remains
responsible for job interpretation only; eligibility, ranking, and assignment
remain deterministic and auditable.

## Data contract

| Feature | Source | Rule |
| --- | --- | --- |
| Service family and required skills | Android job category plus semantic triage | A high-confidence Qwen category may replace the App hint only when description rules agree |
| Skills and declared experience | `Handyman` profile | Canonicalise skills; retain declared experience as profile evidence |
| Completed and cancelled work | `Job` history | Derive counts from assigned jobs; do not hand-enter aggregate counts |
| Category experience | `Job` history | Count completed jobs after canonical category mapping |
| Rating and review count | Customer-authored `Reviews` | Ignore non-customer reviews for provider ranking |
| Active workload | Current `Job` records | Count assigned jobs that are not completed or cancelled |
| Availability and capacity | Profile plus active workload | Explicitly unavailable or at the three-job limit is ineligible |
| Distance | Job and provider service coordinates | Use Haversine distance and retain kilometres as evidence |

Every displayed factor includes its source. Missing history uses a labelled
neutral prior and affects the score, not eligibility by itself.

## Ranking V2

Eligibility is evaluated before scoring: verified, active, available, related
service family, below capacity, and within the recorded service radius.

Relevant experience:

```text
0.30 * specialty match
+ 0.05 * valid declared-years score
+ 0.65 * completed-jobs-in-category score
```

Final score:

```text
0.45 * relevant experience
+ 0.20 * customer rating
+ 0.20 * reliability
+ 0.05 * current workload
+ 0.10 * distance
```

- Declared years saturate at 20 years.
- Declared experience above 50 years is treated as invalid and contributes no
  ranking value until reviewed.
- Category job experience uses a capped logarithmic curve that reaches 1.0 at
  20 completed category jobs.
- Rating uses customer reviews and a clearly labelled neutral prior when there
  is no review history.
- Reliability uses completed versus provider-cancelled work and a clearly
  labelled neutral prior when there is no platform history.
- Current workload uses active jobs against the three-job limit.
- Distance is shown in kilometres; the score is an internal normalisation
  against the provider's service radius.
- Missing provider coordinates or service radius uses a neutral distance value.

## Test data

Automated and integration tests use Firebase Emulator data, not shared Firebase.
The versioned dataset contains:

- at least two eligible providers for each of the 17 Android service families;
- contrast providers with different experience, category history, ratings,
  cancellations, workload, and distance;
- explicit negative cases for unverified, unavailable, at-capacity,
  out-of-radius, and category-mismatch providers;
- cold-start providers with declared experience but no platform history;
- at least 100 labelled job requests covering English, Bangla, vague requests,
  urgency, and all service families;
- job and review records from which all historical aggregates are derived.

Each labelled case records its source type, expected eligible and rejected
providers, expected ordering, and human reviewers. Test labels must not be
generated by the ranking implementation.

## Automatic assignment

`AUTO` mode assigns rank 1 when triage is ready, the candidate passes every hard
rule, and the score is above the configured minimum. Every other case falls back
to `MANUAL_REVIEW`.

Assignment writes must be transactional and idempotent. Stored evidence includes
the assignment mode, ranking version, selected rank, score, and timestamp.

For the local MVP, a separate Firebase worker coordinates automatic assignment.
The mode defaults to `MANUAL`, and enabling `AUTO` only applies to jobs created
after the change. Moving the worker to managed hosting remains a deployment task
and is not part of the local-only phase.

## Delivery order

1. Define the V2 contracts and platform-history aggregation.
2. Add the versioned emulator dataset and independent expected results.
3. Implement and verify Ranking V2.
4. Replace percentage placeholders with recorded values and evidence in the
   Dashboard.
5. Add the `AUTO`/`MANUAL` setting, threshold fallback, transaction, and audit
   record.
6. Verify Android -> Firebase -> ranking -> assignment -> Android/Dashboard end
   to end.

## Acceptance criteria

- zero hard-filter violations;
- deterministic rankings for identical inputs;
- all 17 service families covered;
- no displayed score without a traceable source or labelled neutral prior;
- increasing relevant experience cannot reduce the experience score;
- increasing provider-caused cancellations cannot increase reliability;
- manual mode performs no automatic assignment;
- automatic assignment never exceeds provider capacity or creates duplicate
  assignments;
- full customer app, provider app, Firebase, and Dashboard state agreement.

Firebase security and credential migration are outside this development phase.
